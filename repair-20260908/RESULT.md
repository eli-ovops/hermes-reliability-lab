## 第一性原理结论

收到消息不等于存在订单。可靠自动化必须具备：持久输入 → 已认证的可执行意图 → 唯一执行者 → 交易所回执/未知状态对账 → 持久结果通知。对话模型和 codex-code-mode-host 不应位于这条关键路径；本项目运行入口本来就是 Python/Telethon/OKX SDK，Hermes send 是不调用模型的发送工具。

此前的实现是消息回调内一次性执行；短暂失败后没有 durable job，因此能留下永久 READY。局部重试修复不能填平进程崩溃与任务入账之间的缺口。

## 本次改动

- SQLite schema 4 增加 execution_jobs；原文审计、策略和任务同一事务提交。
- 实盘构建入口改为回调只入账，后台对账通过后处理队列；线程锁与进程锁均保留。
- 只读故障标记 RETRYABLE，持久退避；未知提交结果进入 RECONCILING，禁止盲重放；已完成方向不再提交。
- 重启恢复 RUNNING/PENDING/RETRY；旧 READY 没有新任务，不追溯补挂。被替换、过期、阻断都有明确结局。
- 任务结局和通知同一事务提交；所有方向具有订单 ID 且已对账才记录 DONE。
- 对账一次异常不终止接收/通知循环；Telegram 开启 catch_up，重连调用 connect，退出断开连接；已有数字 ID 不再依赖用户名网络查询。
- 微信调用 --json，仅明确 success 且无 skipped/error 才记 SENT；发送失败保留通知并退避，即使交易暂停也能投递状态。
- 止损/止盈按标签解析，不从止盈区间补造止损，不猜测标签错字；最小价位取整后复核价格方向。
- status.py 提供无网络、无迁移的本地状态读取入口。

## 方案选择依据

原有内存调用无法恢复进程中断；外加 Redis/Celery 等队列会增加部署组件；沿用已存在的 SQLite，可把策略与任务置于同一事务，不新增依赖。

参考：SQLite 官方事务说明 https://www.sqlite.org/lang_transaction.html ；Telethon 官方 client 生命周期与 catch_up 文档 https://docs.telethon.dev/en/stable/modules/client.html 。本地 Hermes hermes_cli/send_cmd.py 的说明与返回值分支用于核对发送契约。

## 重试次数更新
首次尝试失败后自动重试 3 次（等待 30、60、120 秒），共最多 4 次执行尝试。次数随任务持久化；耗尽后明确通知，不无限重试。有效期、暂停、策略替换及未知写结果的对账边界继续生效，重试次数不覆盖这些条件。只更新隔离候选，未部署。新增第四次成功、第四次仍失败后停止的测试。
