# Hermes 自动执行可靠性修复（隔离候选，未部署）

Owner：当前 Hermes 任务。源码基线见 baseline.json。目标：每条新、已认证、参数完整的策略必须有持久执行任务及可查询结局；普通聊天不产生订单。模型对话不在自动执行的关键路径上。

## 根因与验收缺口
- READY 入账后只在 Telegram 回调执行一次；异常/重启/短暂查询失败没有持久续办者。
- 接收回调等待全部交易网络操作，可能延迟其他消息；后台对账异常可终止全部循环。
- 单纯 SUBMITTED 数量不能说明每方向的回执/保护是否完整。
- 通知 CLI 的退出码 0 也可能是 skipped，并不保证送达。
- 已有 HYPE 确认只通过显式历史入口使用；不应把所有含价格的点评扩展成交易规则。

## 候选改动
1. 消息审计、策略、执行任务同一 SQLite 事务；回调只入账。
2. 单执行者周期处理任务，重启恢复；可重试读故障退避；未知写结果先对账，永不盲重放。
3. 接收有效期与执行期限分开记录，沿用现有 5 分钟窗口，不追溯补挂已有 READY；过期显式报告。此参数的业务批准来源仍 UNKNOWN，候选不扩大窗口。
4. 结果通知包含每方向状态与订单 ID；失败任务可检索；JSON success 才标记通知成功。
5. 原始止损/止盈标签按原意解析，价格取整后再次验证；不修改仓位、杠杆等既定参数。

## 必需验收
- 离线：断网、重启、并发、重复消息、未知回执、部分成功、失效/被替换、通知失败、解析矛盾。
- 运行：用户部署后确认加载的代码、账本兼容和监听连接。
- 实盘：新策略的交易所回执以及保护状态，当前尚未验证。

## 边界
本目录无凭证、账户配置、生产账本。所有测试禁止网络。未启动/停止服务、未提交/撤改实盘订单、未修改生产数据库。代码候选不等于生产恢复。
